## 1. 서비스 개요 / 문제 정의

### 1.1 한 줄 정의
모바일 청첩장 서비스. 신랑·신부가 **사진과 텍스트를 입력**하고 **원하는 템플릿을 골라**, **고유 URL을 가진 청첩장 페이지**를 만든다. 하객은 그 URL로 로그인 없이 청첩장을 연다.

### 1.2 해결하려는 문제
- 결혼을 준비하는 신랑·신부는 청첩장을 **직접 디자인하거나 코딩할 수 없다.** 하지만 원하는 분위기(미니멀, 플로럴, 모던 등)는 있다.
- 기존 서비스는 자유도가 지나쳐 완성이 어렵거나(빈 페이지 공포), 반대로 획일적이라 취향을 못 담는다.
- 사진이 많이 들어가는 청첩장 특성상, 업로드가 느리거나 화질이 떨어지면 만족도가 크게 낮아진다.

### 1.3 해결 방식 (제품 가설)
- 디자인은 **사람이 만든 검증된 템플릿(컴포넌트 10~20개)**으로 제한하고, 색·폰트·섹션 순서 등 **조합**으로 다양성을 준다. → 사용자는 "고르고 채우기"만 하면 완성된다.
- 서버가 입력을 **검증**해서, 필드가 비거나 깨진 청첩장이 하객에게 노출되는 일을 막는다. → 완성도 보장.
- 사진은 원본을 안전하게 보관하고 빠르게 보여준다(오브젝트 스토리지 기반).

## 2. 타깃 사용자 & 페르소나

| 구분 | 역할 | 로그인 | 핵심 니즈 |
|---|---|---|---|
| **제작자** (신랑·신부) | 청첩장을 만들고 관리 | 필요 | 쉽게, 예쁘게, 빠르게 완성 |
| **하객** | 청첩장 열람 | 불필요 | 링크 클릭 즉시 잘 보임(모바일) |
| **관리자** | 템플릿 등록·관리 | 필요(내부) | 새 템플릿을 안전하게 추가 |

### 2.1 페르소나 예시
- **제작자 — "지현(30대, 예비 신부)"**: 웹/디자인 지식 없음. 스마트폰으로 저녁에 짬내서 만든다. 사진 20~30장을 올리고 싶고, 결과물이 촌스럽지 않길 원한다. 실패(깨진 화면)에 민감하다.
- **하객 — "민수(청첩장 링크를 받은 지인)"**: 카톡으로 받은 링크를 지하철에서 연다. 로딩이 느리거나 레이아웃이 깨지면 바로 닫는다.
- **관리자 — "운영자(내부 인력)"**: 새 디자인 템플릿을 주기적으로 추가한다. 템플릿의 검증 규칙(JSON Schema)을 등록한다.

## 3. 핵심 유저 시나리오

### 3.1 제작자 — 청첩장 만들기 (핵심 플로우)
1. 회원가입/로그인한다.
2. 템플릿 목록에서 마음에 드는 디자인을 고른다. (카테고리: 미니멀/플로럴/모던 등)
3. 섹션별로 내용을 입력한다. (신랑·신부 이름, 인사말, 예식 정보, 오시는 길, 계좌번호 등)
4. 사진을 업로드한다. → 클라이언트가 스토리지에 직접 올리고, 청첩장 데이터에는 **파일 키/URL만** 담긴다. (상세: ADR-001)
5. 저장을 요청하면 서버가 **선택한 템플릿의 스키마로 입력을 검증**한다. (상세: ADR-002)
   - 통과: 청첩장을 저장하고 **고유 슬러그/URL**을 발급한다.
   - 실패: **어느 필드가 틀렸는지** 알려주고 거절한다. → 제작자가 수정 후 재시도.
6. 발급받은 URL을 하객에게 공유한다.

### 3.2 하객 — 청첩장 열람
1. 공유받은 고유 URL에 접속한다. (로그인 불필요)
2. 프론트(Next.js)가 API로 청첩장 데이터(JSON)를 조회한다.
3. 해당 템플릿의 React 컴포넌트가 JSON을 받아 렌더링한다. 사진은 스토리지/CDN에서 로드된다.

### 3.3 관리자 — 템플릿 등록
1. 새 디자인의 템플릿 메타데이터를 등록한다. (이름, 썸네일, 카테고리, 사용 가능한 섹션, **섹션별 JSON Schema**, 스타일 변형)
2. 프론트에 대응하는 React 컴포넌트를 배포한다.
   - **제약**: `template_id ↔ 프론트 컴포넌트` 매핑이 항상 동기화돼야 한다. DB 등록만으로 템플릿이 "완성"되지 않는다. (상세: ARCHITECTURE.md §6)

## 5. 정책 & 제약

### 5.1 제품 정책
- **디자인 자유 편집 없음.** 사용자는 정해진 템플릿·변형(색/폰트/섹션 순서)만 조합한다. AI 자동 HTML 생성은 도입하지 않는다.
- **완성도 우선.** 스키마 검증을 통과하지 못한 청첩장은 발행되지 않는다. (깨진 화면이 하객에게 노출되지 않게)
- **하객 열람은 무인증 공개.** 고유 URL을 아는 사람은 누구나 열람 가능 → 링크 = 사실상의 접근 권한.

### 5.2 데이터/이미지 정책 (ADR 근거)
- 사진 원본은 **AWS S3**에 저장, 업로드는 **presigned URL로 클라이언트 → S3 직접 업로드**. 서버는 바이너리를 중계하지 않는다. (ADR-001)
- 청첩장 입력값은 **PostgreSQL `jsonb` 단일 컬럼**에 저장. 섹션 스키마는 **JSON Schema 표준**으로 정의하고 저장(write) 시점에 검증. (ADR-002)
- 스키마 **버전 관리는 현 단계 미도입**. 운영 중 스키마 변경 시 기존 데이터와 어긋날 수 있음 → 후속 과제.

### 5.3 알고 받아들이는 제약
- 새 템플릿 = **DB 등록 + 프론트 컴포넌트 배포**. 둘의 매핑 동기화가 전제.
- 서버가 이미지 내용을 직접 보지 못해, 위장 파일 등은 업로드 후 검증으로 보강해야 한다. (ADR-001)
- jsonb라 DB 레벨 무결성이 약함 → **서버 검증을 신뢰**하는 것이 전제.

## 6. 성공지표 (KPI)

> 초기 가설 검증용 지표 제안. 구체 목표 수치는 데이터 확보 후 확정.

| 구분 | 지표 | 의미 |
|---|---|---|
| 활성화 | 청첩장 **발행 완료율** (가입 대비 발행) | "고르고 채우기" 가설이 통하는가 |
| 완성 경험 | 제작 시작 → 발행까지 **소요 시간** | 쉽고 빠른가 |
| 품질 | **검증 실패율** / 실패 후 재시도 성공률 | 검증이 도움을 주는가, 막기만 하는가 |
| 하객 경험 | 청첩장 **열람 성공률·로딩 시간** | 링크 클릭이 열람으로 이어지는가 |
| 콘텐츠 | 청첩장당 **평균 사진 수 / 업로드 실패율** | 핵심 입력(사진)이 원활한가 |
| 확장 | **템플릿별 사용 분포** | 어떤 디자인이 사랑받는가 |

## 7. 범위 / 비범위

### 7.1 이번 범위 (In Scope)
- 제작자 인증, 템플릿 조회/등록, 청첩장 제작·검증·발행, 사진 업로드, 하객 공개 열람 (REST API).

### 7.2 비범위 (Out of Scope)
- 프론트엔드 렌더링(별도 Next.js 레포 담당) — 서버는 데이터·검증만.
- 결제/유료화, 정산.
- 청첩장 내 디자인 자유 편집기, AI 자동 생성.
- 방명록/RSVP 등 부가 상호작용(추후).
