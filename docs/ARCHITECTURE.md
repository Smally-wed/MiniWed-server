# MiniWed 서버 아키텍처 개요

> 이 문서는 MiniWed 서버의 전체 그림을 한눈에 보기 위한 **기준점 문서**입니다.
> 개별 의사결정의 배경과 트레이드오프는 `docs/adr/`의 ADR 문서에서 다룹니다.
>
> - 최초 작성일: 2026-06-30
> - 상태: 초안 (일부 항목 미정 — 아래 "미결정 / 후속 ADR" 참고)

## 1. 제품 한 줄 요약

모바일 청첩장 서비스. 사용자(신랑·신부)에게 **사진과 텍스트를 받아**, 사용자가 **고른 템플릿**에 넣어 **고유 URL을 가진 청첩장 페이지**를 만들어 준다. 하객은 그 URL로 청첩장을 열람한다.

## 2. 핵심 설계 원칙

- **템플릿 = 데이터 + 렌더러 분리.** 서버는 청첩장의 *데이터*만 저장하고, *디자인(렌더링)*은 프론트엔드가 전담한다. 서버는 HTML/CSS를 들고 있지 않는다.
- **서버가 입력을 검증한다.** 사용자가 보낸 청첩장 데이터(JSON)를, 해당 템플릿이 요구하는 섹션 스키마에 맞는지 서버가 검증한 뒤 저장한다. 깨진 청첩장이 하객에게 노출되지 않도록 하는 것이 목적이다.
- **AI 자동 HTML 생성은 도입하지 않는다.** 템플릿은 사람이 만든 컴포넌트 10~20개로 두고, 색·폰트·섹션 순서 등 조합으로 다양성을 준다.

## 3. 구성 요소 (Components)

| 구성 요소 | 역할 |
|---|---|
| 제작자 (신랑·신부) | 회원가입/로그인 후 청첩장을 만든다 |
| 하객 | 고유 URL로 청첩장을 열람한다 (로그인 불필요) |
| 관리자 | 템플릿을 등록·관리한다 (현재는 이 서버를 통해) |
| **REST API 서버 (이 레포)** | 인증, 템플릿 메타데이터 관리, 청첩장 데이터 저장·검증·조회 (JSON API) |
| Next.js 프론트엔드 (별도 레포) | 사용자 입력 화면 + 템플릿별 React 컴포넌트로 청첩장 렌더링 |
| PostgreSQL | 사용자·템플릿 메타데이터·청첩장 데이터 저장 |
| 이미지 스토리지 | 업로드된 사진 원본 저장 (저장 방식은 ADR-001에서 결정) |

## 4. 주요 데이터 흐름

1. **제작자 회원가입/로그인** — 계정 기반으로 자신의 청첩장을 관리한다.
2. **템플릿 선택 + 입력** — 텍스트(신랑·신부 이름, 인사말, 예식 정보 등)와 사진을 입력한다. 사진은 이미지 스토리지에 업로드되고, 청첩장 데이터에는 **파일 키/URL만** 들어간다 (바이너리 아님).
3. **검증 후 저장** — 서버가 선택된 템플릿의 섹션 스키마로 입력 JSON을 검증한다. 통과하면 청첩장을 저장하고 **고유 슬러그/URL**을 발급한다.
4. **하객 열람** — 하객이 고유 URL에 접속하면, 프론트가 API로 청첩장 데이터를 조회하고 해당 템플릿 컴포넌트가 JSON을 받아 렌더링한다.

## 5. 데이터 모델 개요 (잠정)

> 상세 스키마·검증 방식은 ADR(데이터 모델 / 템플릿 렌더링)에서 확정한다. 아래는 방향성만.

**템플릿 메타데이터**
- `template_id`, `name`, `thumbnail`, `category` (미니멀 / 플로럴 / 모던 등)
- 사용 가능한 섹션 목록 (예: 커버, 인사말, 갤러리, 예식정보, 오시는길, 계좌번호, 방명록)
- **각 섹션이 요구하는 필드 스키마** (서버 입력 검증의 근거)
- 섹션별 스타일 변형(variant) 옵션

**사용자 청첩장 데이터**
- `invitation_id`, `user_id`, `template_id`, `slug`, `status`
- 섹션별 입력값 (JSON): `{ groom_name, bride_name, date, photos: [키/URL...], greeting_text, ... }`

## 6. 핵심 결정 사항

| 결정 | 현재 상태 | 비고 |
|---|---|---|
| 데이터/렌더러 분리 | 채택 | 서버는 데이터·검증, 프론트는 렌더링 |
| 입력 검증 책임 = 서버 | 채택 | 템플릿 섹션 스키마로 서버가 검증 |
| 템플릿 관리 위치 | 현재 이 서버 | 추후 별도 서비스로 분리 가능성 열어둠 |
| 프론트 = 별도 Next.js 레포 | 채택 | 이 레포는 REST API만 제공 |
| 청첩장 공개 방식 = 고유 URL/슬러그 | 채택 | 하객은 로그인 없이 열람 |

### 알고 받아들이는 제약
- **새 템플릿 추가 = DB 등록 + 프론트 배포.** `template_id`는 DB 행이지만 실제 화면은 프론트의 React 컴포넌트다. 따라서 `template_id ↔ 프론트 컴포넌트` 매핑이 항상 동기화돼야 한다. 관리자가 DB만으로 새 템플릿을 "완성"할 수는 없다.

## 7. 미결정 / 후속 ADR

| 주제 | 메모 |
|---|---|
| ADR-001 사진(이미지) 저장·전송 방식 | 오브젝트 스토리지 vs DB vs 로컬 FS |
| ADR-002 데이터 모델 & 템플릿 렌더링·검증 상세 | 섹션 스키마 정의 방식(JSON Schema 등), 검증 시점, 스키마 버전 관리 |
| 인증/인가 상세 | 회원가입/로그인 방식, 하객 공개 페이지의 인증 경계 |
