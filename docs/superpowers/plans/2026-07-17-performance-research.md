# MVP 성능·운영 연구 계획

> **문서 성격**: 구현 계획이 아니라 **연구 계획**이다. 기존 `plans/`의 태스크 체크박스 형식(subagent-driven-development)을 따르지 않는다. 각 연구는 "같은 기능을 하는 변형 메서드를 2~4개 만들어 비교"하는 구조다.

**작성일**: 2026-07-17
**전제**: 이번 주 기능 개발 완료 후 착수
**Goal**: 하객 로드 1초 / 청첩장 생성 1초라는 제품 요구사항을, 근거 있는 수치로 달성 가능한지 검증하고 설계 결정을 데이터로 확정한다.

## 0. 예산 도출 — 모든 목표 수치의 출처

이 문서의 모든 목표치는 **지어낸 값이 아니라 아래 두 요구사항에서 거꾸로 쪼갠 값**이다. 요구사항이 바뀌면 전부 재계산한다.

### 기준점 (제품 요구사항)

| 요구사항 | 값 | 출처 |
|---|---|---|
| 하객 청첩장 로드 | **≤ 1,000ms** (절대 조건) | 사용자 지정 |
| 청첩장 생성/저장 | **≤ 1,000ms** | 사용자 지정 |

### 로드 1,000ms 분해

| 구간 | 예산 | 담당 | 관련 연구 |
|---|---|---|---|
| DNS + TLS + 모바일 네트워크 왕복 | 250ms | 인프라 | Phase 0 실측 |
| **서버 API (청첩장 조회)** | **100ms** | 이 서버 | **연구 C** |
| Next.js SSR + 하이드레이션 | 200ms | 프론트 레포 | 범위 밖 |
| **이미지 로드 (LCP 요소)** | **400ms** | S3/CDN | **연구 E** |
| 버퍼 | 50ms | | |

**서버 API 몫은 전체의 10%다.** 이미지가 40%를 먹는다. 이 비율이 연구 우선순위를 정한다.

### 저장 1,000ms 분해

| 구간 | 예산 | 관련 연구 |
|---|---|---|
| 네트워크 왕복 | 250ms | Phase 0 |
| **서버 저장 API** | **700ms** | |
| └ 그중 JSON Schema 검증 | **10ms** (1.5%) | **연구 A** |
| └ 나머지 (DB write 등) | 690ms | |
| 버퍼 | 50ms | |

### 이미지 크기 상한 — 대역폭 역산

```
전송 가능 크기 = 이미지 예산(400ms) × 모바일 실효 대역폭
  10 Mbps → 500KB
   5 Mbps → 250KB
```

하객이 청첩장을 여는 상황은 **예식장 근처·이동 중** — 사람이 몰려 네트워크가 가장 나쁜 환경이다. 보수적으로 잡는다.

> **도출 결과: 첫 화면 이미지 ≤ 300KB**

아이폰 원본 사진은 3~5MB다. 10Mbps에서 3MB = 2.4초. **서버 API가 0ms여도 1초 목표는 깨진다.** 이것이 연구 E를 최우선에 두는 이유다.

### 부하 계산

```
동시 발행 100건 × 하객 300명 × 재방문 2.0회 = 60,000 조회
피크(발송 후 10분에 20% 집중)  = 12,000 / 600초 ≈ 20 RPS
보수적 피크(5분에 30%)         = 18,000 / 300초 ≈ 60 RPS
```

**피크 20~60 RPS.** Postgres가 힘들어할 규모는 아니다. 따라서 연구 C의 질문은 "캐시를 어떻게 잘 할까"가 아니라 **"캐시가 애초에 이득인가"**여야 한다.

- [ ] **측정 환경 고정** — 동일 머신, 전원 연결, 타 프로세스 종료, CPU 거버너 고정

### ⚠️ JMH 없이 재면 결과가 뒤집힌다

JVM은 JIT 워밍업 때문에 **먼저 실행한 구현이 느리게 나온다.** `System.nanoTime()`으로 재면 순서만 바꿔도 승자가 바뀐다. 변형 메서드 비교 방식에서는 치명적이다.

**도구 분리**: 연구 A·B는 CPU 마이크로벤치마크 → **JMH**. 연구 C·D는 워크로드 시뮬레이션 → **k6**. 연구 E는 네트워크 측정 → **브라우저/실기기**.

## 연구 E. S3 직접 vs CloudFront (2일) — 최우선

> **ADR-001 후속 조치 "공개 읽기 제공 방식 결정: S3 공개 읽기 vs CloudFront 배포 (CloudFront 권장, 별도 검토)"를 데이터로 닫는다.** 새 연구가 아니라 미결 결정의 종결이다. 결과는 ADR-001에 "확정 사항"으로 추가한다.

**질문**: 1초 예산의 40%를 쥔 이미지를 400ms 안에 내릴 수 있는가? CDN과 이미지 최적화 중 무엇이 지배적인가?

**전제 확인 완료**: ADR-001상 presigned URL은 **업로드 전용**, 읽기는 **공개 읽기**. → CDN 캐싱과 서명 URL의 충돌 문제 없음.

### 변형 — 2×2 요인 설계

같은 기능: "청첩장 이미지를 하객에게 전달"

| | 원본 그대로 | 리사이즈 + WebP |
|---|---|---|
| **S3 직접** | **E1** (현재 구조, baseline) | **E2** |
| **CloudFront** | **E3** | **E4** |

**4개를 다 만드는 이유**: 두 요인을 분리하기 위해서다. 2개만 비교하면 구분이 안 된다.
- E1→E2가 크고 E1→E3가 작으면 → **최적화가 본질, CDN은 보조**
- E1→E3가 크고 E1→E2가 작으면 → **거리가 본질**
- E4만 목표 달성 → **둘 다 필요**

### 실험 설계

- **콜드 캐시 / 웜 캐시를 반드시 분리 측정.** 첫 하객은 오리진 fetch라 오히려 느리다. 섞어 재면 CDN이 부당하게 나쁘게 나온다.
  - 실제 미스율 추정: 청첩장 100건 × 사진 10장 = 1,000객체를 각 300명이 조회 → 미스 ≈ 1/300
- **네트워크 조건**: Chrome DevTools 스로틀링(Fast 3G / LTE) + 가능하면 실기기 실측
- **측정 대상**: 첫 화면 LCP 이미지 1장 기준 (lazy load 대상 제외)

### 테스트 횟수

| 항목 | 값 | 이유 |
|---|---|---|
| 조합당 반복 | **50회** | 네트워크 측정은 분산이 커서 JMH급 반복 불가, 대신 표본 확보 |
| 통계량 | **중앙값 + p95** | 평균은 네트워크 이상치에 오염됨 |
| 콜드/웜 | **각각 별도 50회** | 섞으면 무의미 |
| 총 실행 | 4조합 × 2상태 × 50회 = **400회** | |

### 목표 지표

| 지표 | 목표 | 도출 |
|---|---|---|
| **첫 화면 이미지 크기** | **≤ 300KB** | 400ms × 5Mbps 역산 (G7) |
| **첫 이미지 로드 p95 (웜)** | **≤ 400ms** | 1초 예산 분해 |
| 첫 이미지 로드 p95 (콜드) | ≤ 800ms | 300명 중 1명만 겪음 |
| 엣지 캐시 히트율 | **≥ 95%** | 미스 1/300 구조상 달성 가능 |
| egress 비용 | E1 대비 절감률 측정 | CloudFront 단가 확인 필요 |

### 파급

E에서 "최적화 필수"가 나오면(가능성 높음) **이미지 리사이징/변환 파이프라인 개발이 새 범위로 들어온다.** 그래서 맨 앞에 둔다 — 빨리 아는 게 낫다.

## 연구 A. JSON Schema 검증 비용 (2일)

**질문**: 스키마 컴파일이 검증 대비 몇 배 비싼가? 캐싱하면 무엇이 사라지는가?

### 변형

같은 기능: "청첩장 JSON을 템플릿 스키마로 검증" (기존 `core/validation/SchemaValidator` 경유)

| 변형 | 구현 | 역할 |
|---|---|---|
| **A1** | 매 호출마다 DB 스키마 조회 → `getSchema()` 컴파일 → 검증 | baseline (현재 구조 추정) |
| **A2** | 컴파일된 `JsonSchema`를 로컬 캐시(Caffeine) → 검증 | 컴파일 비용 제거 |
| **A3** | 스키마 원문 Redis 캐시 + 컴파일 결과 로컬 캐시 → 검증 | 다중 인스턴스 대응 |

> **A3가 필요한 구조적 이유**: `JsonSchema` 객체는 직렬화 불가 → Redis에 컴파일 결과를 넣을 수 없다. 인스턴스가 늘면 각자 컴파일해야 하고 Redis엔 **원문만** 캐시된다. 이 제약을 실험으로 확인하는 게 A3의 목적이다.

### 실험 설계

**비용을 3개로 분리 측정한다.** 뭉뚱그리면 병목 위치를 알 수 없다.
1. DB 스키마 조회 2. 컴파일 3. 검증 실행

**파라미터** (`@Param`): 스키마 필드 수 `{10, 50, 200}` × 중첩 깊이 `{1, 3, 5}` = **9조합**

### 테스트 횟수

```java
@Fork(5)                                    // JVM 5개 — JIT 편차 흡수
@Warmup(iterations = 10, time = 1)          // 워밍업
@Measurement(iterations = 20, time = 1)     // 변형당 100회 측정
@BenchmarkMode(Mode.SampleTime)             // p99 필요 → 평균 모드 금지
@OutputTimeUnit(TimeUnit.MICROSECONDS)
```

**소요**: 3변형 × 9조합 × 150s ≈ **70분/1회 실행**

### 목표 지표

| 지표 | 목표 | 도출 |
|---|---|---|
| **A2 검증 p99** (최악: 필드 200 × 깊이 5) | **≤ 10ms** | 저장 예산 700ms의 1.5% |
| 컴파일:검증 비율 | **측정값** — 10배 초과 시 캐싱 필수 확정 | 판정 규칙 |
| A1 대비 A2 개선 | **99.9% 신뢰구간 비중첩** | 겹치면 "차이 없음"이 결론 |
| **allocation** (`-prof gc`) | **≤ 10KB/op** | 초당 1000건 = 10MB/s GC 압력 |

**allocation을 반드시 잰다.** 지연만 보면 빨라 보이는데 GC를 유발해 **다른 요청의 p99를 망가뜨리는** 경우가 있다.

## 연구 B. Redis 직렬화 (1일)

**질문**: `@class` 타입 정보의 대가는 얼마인가?

### 변형

같은 기능: "객체를 Redis에 저장/조회" (`config/RedisConfig`, `core/cache/RedisCacheService`)

| 변형 | 구현 | 특성 |
|---|---|---|
| **B1** | `GenericJacksonJsonRedisSerializer` | **현재 코드**. payload에 `@class` 포함 |
| **B2** | `Jackson2JsonRedisSerializer<T>` (타입 고정) | 타입 정보 없음, 캐시별 타입 선언 필요 |
| **B3** | `StringRedisSerializer` + 수동 `ObjectMapper` | 완전 제어, 보일러플레이트 증가 |

> Kryo·Protobuf는 제외. 직렬화 CPU가 병목이라는 증거가 없고 스키마 관리 비용이 MVP에 과하다. B1~B3에서 결론이 안 나면 그때 연다.

### 실험 설계 — 성능보다 정확성이 핵심

**리팩터링 내구성 테스트** (가장 중요):
1. 각 변형으로 객체를 Redis에 저장
2. 클래스를 **다른 패키지로 이동**
3. 역직렬화 시도 → 성공/실패 기록

B1은 여기서 깨질 가능성이 높다. **지금 컴포넌트 도메인 구조를 활발히 재설계 중이므로**(ADR-007, 미커밋 신규 도메인 다수) 이론이 아니라 실제로 겪을 일이다.

**객체 크기 파라미터**: `{작은 DTO(~200B), 중간(~2KB), 청첩장 전체(~20KB)}`

### 테스트 횟수

| 항목 | 값 | 이유 |
|---|---|---|
| 직렬화/역직렬화 지연 | JMH `@Fork(5) @Warmup(10) @Measurement(20)`, `Mode.SampleTime` | |
| payload 크기 | **1회** | 결정론적 계산이라 반복 불필요 |
| Redis 메모리 | `MEMORY USAGE` 커맨드 실측 | 추정 아닌 실측 |
| 리팩터링 내구성 | 변형당 1회 | 합격/불합격 |

### 목표 지표

| 지표 | 목표 | 도출 |
|---|---|---|
| **패키지 이동 후 역직렬화** | **성공** (탈락 조건) | 실패 시 운영 중 캐시 전면 무효화 |
| `@class` 오버헤드 비율 (작은 DTO) | **≤ 15%** | 초과 시 B2 전환 근거 |
| 캐시 1건당 Redis 메모리 | **≤ 10KB** | 청첩장 10만 건 × 10KB = 1GB 인스턴스 |
| 역직렬화 p99 (20KB) | **≤ 10ms** | 조회 예산 100ms의 10% |

마지막이 아니라 **첫 항목이 합격/불합격**이다. 여기서 떨어지면 지연이 아무리 좋아도 탈락.

## 연구 C. 캐시 전략 (2일)

**질문**: ~~도메인별 히트율이 유의미한가~~ → **이 규모에서 캐시가 애초에 이득인가? 언제부터 필요해지는가?**

### 질문을 바꾼 이유

캐시의 효용은 둘인데 이 규모에선 하나가 죽는다.
- **DB 부하 감소** → 20~60 RPS라 불필요. **죽음.**
- **지연 감소** → 살아있음. 단 Redis 왕복도 네트워크 1회고 Postgres PK 조회도 이미 빠르다. 캐시가 이기려면 조인·jsonb 파싱 비용이 그만큼 커야 한다.

`Invitation` 엔티티는 `Template` 조인(`ManyToOne`) + `sectionValues` jsonb 파싱이 있어 순수 PK 조회가 아니다. **해봐야 안다.**

> **C1(캐시 없음)이 이길 수 있고, 그건 실패가 아니다.** "이 규모에선 캐시를 넣지 않는다"는 근거 있는 결정이며 Redis 운영 부담을 정당하게 덜어낸다. 히트율 87% 같은 숫자보다 값지다.

### 변형

같은 기능: "슬러그로 청첩장 조회" (`Invitation.slug`, 발행 상태만 공개)

| 변형 | 구현 | 위험 |
|---|---|---|
| **C1** | 캐시 없음, DB 직행 | baseline |
| **C2** | Cache-aside + TTL | **stale read 발생** |
| **C3** | Cache-aside + 수정/발행 시 명시적 무효화 | 무효화 누락 시 영구 stale |
| **C4** | C3 + 보험용 TTL 병행 | 복잡도 증가 |

### 🚨 stale read는 성능이 아니라 정확성 문제

C2의 TTL 구간 동안 **신랑신부가 예식 시간을 고쳤는데 하객이 옛날 정보를 본다.** 예식 시간이 틀린 청첩장은 이 서비스에서 **치명적 결함**이지 성능 저하가 아니다.

> **히트율 90%인 C2가 stale read를 1건이라도 내면, 히트율 70%인 C3에게 진다.**

### 실험 설계 — 한 점이 아니라 곡선

100건은 하한이므로 계단식으로 올려 **캐시가 필요해지는 지점**을 찾는다.

| 규모 | 피크 RPS | 알아낼 것 |
|---|---|---|
| **100건** | 20~60 | 현재 목표. C1이 100ms를 지키는가? |
| 300건 | 60~180 | |
| 1,000건 | 200~600 | **캐시 없이 버티는 상한** |

결론이 "캐시 넣자/말자"가 아니라 **"현재 규모는 X, 캐시가 필요해지는 건 Y건부터"**가 된다. 운영 트리거로 바로 쓴다.

### 테스트 횟수

| 항목 | 값 | 이유 |
|---|---|---|
| 워밍업 제외 구간 | **5분** | 캐시 콜드 스타트가 히트율을 왜곡 |
| 측정 구간 | **30분** | 정상상태(steady state) 도달 후 |
| 시나리오당 반복 | **3회, 중앙값** | 단발 측정은 신뢰 불가 |
| 총 조합 | 4변형 × 3규모 × 3회 = **36회 × 35분 ≈ 21시간** | 야간 배치 권장 |

### 목표 지표

| 지표 | 목표 | 도출 |
|---|---|---|
| **stale read** | **0건** (탈락 조건) | 예식 시간 오류는 치명적 |
| **무효화 누락** | **0건** — 편집 후 즉시 재조회 시 신규 데이터 | 정확성 |
| **조회 API p99 (히트)** | **≤ 100ms** | 1초 예산의 10% |
| 조회 API p99 (미스) | ≤ 200ms | |
| **캐시 채택 판정** | C2/C3/C4가 C1을 **99.9% 신뢰구간 비중첩**으로 이겨야 채택 | 못 이기면 미도입 |
| 캐시 필요 임계점 | **건수로 특정** | 운영 트리거 |

## 연구 D. 검색 최적화 (1.5일)

> **⚠️ 확인 필요**: 검색 **대상**이 아직 불명확하다. 현재 리포지토리는 전부 단일 키 조회(`findByEmail`, `findByKey`, `findTemplateByTemplateUid`)뿐이라 검색할 대상이 없다. 아래는 두 경우를 모두 커버한 초안이며, 기능 정의 후 해당 분기만 남긴다.

**분기**:
- **(가) 일반 컬럼 검색** (템플릿 제목·카테고리 필터 등) → B-tree 인덱스 경로
- **(나) jsonb 내부 검색** (`sectionValues`·`optionSchema` 내부 키/값) → GIN 인덱스 경로

### 변형

| 변형 | 구현 | 적용 분기 |
|---|---|---|
| **D1** | 인덱스 없음 | baseline (가·나 공통) |
| **D2** | B-tree 인덱스 | (가) |
| **D3** | jsonb GIN 인덱스 | (나) |
| **D4** | D2/D3 승자 + 캐싱 | 공통 |

### ES 질문의 재설계

"ES가 과도한 설계인가?"는 실험 없이 답이 정해져 있다(**과하다** — 템플릿 수백 건 규모). 실험으로 증명하는 건 시간 낭비다. 대신 **임계점을 찾는다**:

> 데이터 건수를 **10² → 10³ → 10⁴ → 10⁵ → 10⁶**으로 늘리며 응답시간 곡선이 꺾이는 지점을 특정한다.

산출물이 "지금은 인덱스로 충분, **N건 초과 시 ES 검토**"라는 **운영 트리거**가 된다. ES를 실제 구축해 비교하는 것보다 훨씬 싸고 유용하다. 연구 C의 캐시 임계점과 같은 모양.

### 테스트 횟수

| 항목 | 값 |
|---|---|
| 데이터 규모 | 5단계 (10²~10⁶) |
| 규모당 쿼리 실행 | 100회, p95/p99 |
| 반복 | 3회, 중앙값 |
| `EXPLAIN ANALYZE` | 각 조합 1회, 실행 계획 기록 |

### 목표 지표

| 지표 | 목표 |
|---|---|
| 검색 p99 (10⁴건) | **≤ 50ms** (목록 조회는 LCP 임계경로 밖이라 조회 API보다 여유) |
| **`EXPLAIN ANALYZE`** | **Seq Scan 0건** — 전부 Index Scan |
| **ES 검토 임계점** | **곡선 변곡점을 건수로 특정** |
| 인덱스 쓰기 오버헤드 | 등록 API p99 저하 ≤ 10% |

### 별건 — 연구 아님 (30분)

`Template.templateUid`, `Component.componentUid`, `User.email`, `OptionDefinition.key` 컬럼에 **유니크 인덱스가 실제로 걸려 있는지 확인.** `ddl-auto: create-drop`이라 엔티티 애노테이션에만 의존한다. (`Invitation.slug`는 `@UniqueConstraint(name = "uk_invitation_slug")`로 확인됨.) 체크리스트지 연구가 아니다.

## 일정 (8.5일)

| 일 | 작업 | 근거 |
|---|---|---|
| 0.5 | **Phase 0** — JMH, 기준선, 대역폭 실측 | 전 연구의 전제 |
| 1~2 | **연구 E (S3 vs CDN)** | 예산의 40%, ADR-001 종결, 새 범위 유발 가능 |
| 3~4 | **연구 A (JSON Schema)** | 결과가 C의 캐싱 대상을 바꿀 수 있음 |
| 5 | **연구 B (Redis 직렬화)** | 리팩터링 중이라 시급 |
| 6~7 | **연구 C (캐시 곡선)** | 야간 배치 활용 |
| 8~8.5 | **연구 D (검색)** | |

**순서의 근거**:
- E가 1순위 — 1초 목표의 최대 위협이고, "최적화 필수" 결론이 나오면 이미지 파이프라인 개발이 새 범위로 들어온다. 빨리 알아야 한다.
- A가 C보다 앞 — A에서 "스키마 컴파일 캐싱 필수"가 나오면 **그게 C가 찾던 진짜 캐싱 대상**일 수 있다. 순서가 정보를 만든다.
- B가 C보다 앞 — C에서 캐시를 채택하면 B의 직렬화 결정이 이미 나와 있어야 한다.

## Global Constraints

- **측정 도구 분리**: A·B = JMH(마이크로벤치마크), C·D = k6(워크로드), E = 브라우저/실기기(네트워크). 섞지 않는다.
- **JMH 필수**: `System.nanoTime()` 직접 측정 금지. JIT 워밍업으로 결과가 뒤집힌다.
- **승자 판정**: 99.9% 신뢰구간이 겹치면 "차이 없음"이 결론이다. 겹치는데 승자를 선언하지 않는다.
- **탈락 조건 우선**: stale read(C), 패키지 이동 후 역직렬화(B)는 성능과 무관한 합격/불합격이다. 지연이 좋아도 탈락시킨다.
- **baseline 필수**: 모든 연구에 "아무것도 안 한 변형"(A1/B1/C1/D1/E1)을 둔다. 개선을 못 이기면 도입하지 않는다.
- **빌드 훅**: 모든 Edit/Write가 전체 `./gradlew build`(Postgres/Redis/jwt.secret 필요)를 돌린다. 인프라 부재로 실패해도 파일은 반영된다.
- **범위 밖**: 프론트(Next.js) 렌더 성능, 인프라 스케일링, Actuator/관측성 도입, DB 마이그레이션 도구(Flyway) — 별도 과제.
