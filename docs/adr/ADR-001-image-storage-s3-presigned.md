# ADR-001: 사진 저장은 AWS S3, 업로드는 presigned URL 직접 업로드

- 상태: 승인됨
- 작성일: 2026-06-30
- 작성자: jasmin
- 관련 ADR: 없음

## 배경 (Context)

MiniWed는 사용자(신랑·신부)에게 사진을 받아 청첩장에 넣어주는 서비스다. 사진은 이 제품의 핵심 입력이며, 청첩장 한 건에 다수의 고화질 이미지가 포함될 수 있다.

- 사진 원본 파일을 **어디에 저장**할지 결정해야 한다.
- 청첩장 데이터(JSON)에는 파일 자체가 아니라 **저장소 키/URL만** 들어가기로 이미 정했다([docs/ARCHITECTURE.md](../ARCHITECTURE.md)).
- 배포 환경은 AWS로 정해져 있다.
- 청첩장은 하객이 로그인 없이 고유 URL로 열람하므로, 이미지도 **공개 읽기**가 가능해야 한다.

이미지 같은 큰 바이너리는 용량·성능·비용 측면에서 RDB(PostgreSQL)에 직접 담기 부적합하고, 단일 서버 로컬 디스크는 확장·백업·다중 인스턴스 운영에 제약이 크다. 따라서 저장 방식과 업로드 경로를 결정한다.

## 결정 (Decision)

**사진 원본은 AWS S3에 저장한다.** 청첩장 데이터에는 S3 객체 키(또는 그로부터 만든 URL)만 저장한다.

**업로드는 presigned URL을 통한 클라이언트 → S3 직접 업로드 방식**을 사용한다. 즉, 클라이언트가 서버에 업로드 URL을 요청하면, 서버가 인증·제약 조건(파일 타입·크기 등)을 검증한 뒤 presigned URL과 객체 키를 발급하고, 클라이언트는 그 URL로 S3에 직접 파일을 올린다. 서버는 바이너리를 중계하지 않는다.

대략적인 흐름:
1. (로그인 사용자) 클라이언트가 서버에 업로드 요청 — 파일명·content-type 등 전달
2. 서버가 권한·제약을 확인하고 객체 키를 정한 뒤 presigned URL 발급
3. 클라이언트가 presigned URL로 S3에 직접 PUT/POST
4. 클라이언트가 업로드 완료된 키를 청첩장 데이터에 포함해 서버에 저장 요청
5. 서버는 해당 키를 청첩장 JSON에 저장

## 고려한 대안 (Alternatives Considered)

### 대안 1: 서버 경유 업로드 (클라이언트 → 서버 → S3)
- 설명: 클라이언트가 멀티파트로 서버에 올리면, 서버가 파일을 받아 검증 후 S3에 업로드.
- 장점: 서버가 실제 파일 내용을 직접 보므로 검증(이미지 디코드, 변환, 리사이즈)이 쉽다.
- 단점: 모든 사진 트래픽이 서버를 통과해 메모리·대역폭·비용 부담이 크다. 고화질 다수 업로드 시 병목.
- 채택하지 않은 이유: 사진이 많고 큰 서비스 특성상 서버 중계 비용이 크다. 검증은 presigned 방식에서도 후처리로 보강 가능하다.

### 대안 2: DB(PostgreSQL bytea)에 직접 저장
- 설명: 이미지 바이너리를 RDB 컬럼에 저장.
- 장점: 별도 스토리지·트랜잭션 정합성 고민이 없고 구현이 단순.
- 단점: DB 용량·백업 크기 급증, 조회 성능 저하, 비용 비효율. 대용량 바이너리에 부적합.
- 채택하지 않은 이유: 이미지 규모·성격에 맞지 않는다.

### 대안 3: 서버 로컬 파일시스템
- 설명: 서버 디스크에 파일을 저장하고 경로를 DB에 기록.
- 장점: 초기 구현이 가장 단순.
- 단점: 다중 인스턴스 확장 불가, 백업·내구성·CDN 연동 어려움.
- 채택하지 않은 이유: 확장성과 운영 안정성에서 S3에 크게 밀린다.

## 결정 이유 (Rationale)

- **운영 안정성·확장성**: S3는 내구성·가용성이 높고, 다중 인스턴스 서버 구성과 무관하게 동작한다. 배포 환경이 AWS라 연동이 자연스럽다.
- **서버 부하 절감**: presigned 직접 업로드는 사진 바이너리가 서버를 거치지 않아, 트래픽·메모리 비용을 줄인다. 고화질 사진이 많은 서비스에 유리하다.
- **데이터/저장소 분리 원칙과 일치**: 청첩장 데이터에는 키/URL만 두기로 한 기존 결정과 맞물린다.

## 영향 (Consequences)

### 긍정적 영향
- 서버는 사진 트래픽을 중계하지 않아 가볍게 유지된다.
- 스토리지 확장·내구성·백업을 AWS에 위임할 수 있다.
- CDN(CloudFront) 연동, 이미지 캐싱으로 하객 열람 성능을 높일 여지가 있다.

### 부정적 영향 / 트레이드오프
- **서버가 파일 내용을 직접 보지 못한다.** content-type·크기는 presigned 조건(content-length-range 등)으로 제한할 수 있으나, 확장자를 위장한 비이미지 파일 등은 업로드 시점에 막기 어렵다. → 업로드 후 검증(이미지 디코드/썸네일 생성, 또는 S3 이벤트 기반 검증)으로 보강이 필요하다.
- **고아 객체(orphan) 문제.** 클라이언트가 S3에 올리기만 하고 청첩장 저장을 완료하지 않으면, 어느 청첩장에도 연결되지 않은 파일이 남는다. → 임시 경로 업로드 후 확정 시 연결, S3 lifecycle 규칙으로 미연결 객체 정리 등의 정책이 필요하다.
- 업로드 흐름이 서버 경유보다 단계가 많아 클라이언트·서버 간 약속(키 규칙, 완료 통지)이 더 필요하다.

### 후속 조치 필요 사항
- 객체 키 구조 설계 (예: `invitations/{invitationId}/{uuid}.jpg` 또는 임시→확정 경로 분리)
- 공개 읽기 제공 방식 결정: S3 공개 읽기 vs CloudFront 배포 (캐싱·보안 측면에서 CloudFront 권장, 별도 검토)
- presigned 발급 시 제약 조건(허용 content-type, 최대 크기) 확정
- 업로드 후 이미지 검증·고아 객체 정리 정책 확정
- presigned 발급 API는 로그인 사용자만 호출 가능하도록 인증 연계
