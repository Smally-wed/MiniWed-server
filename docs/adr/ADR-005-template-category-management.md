# ADR-005: 템플릿 카테고리를 관리 리소스로 두고 등록 시 존재를 앱에서 검증

- 상태: 승인됨
- 작성일: 2026-07-14
- 작성자: jasmin
- 관련 ADR: ADR-002

## 배경 (Context)

ADR-002에서 `templates` 테이블에 `category`를 단순 문자열 필드로 두기로 했다. 그런데 현재 구현은 다음 문제가 있다.

- `Template.category`가 자유 문자열이라, 존재하지 않는(오타 포함) 카테고리가 그대로 저장된다.
- 별도의 `Category` 엔티티/테이블/서비스가 이미 존재하지만, 템플릿 등록 로직과 전혀 연결돼 있지 않다. 즉 관리 대상 카테고리 목록과 실제 템플릿의 카테고리 값이 어긋날 수 있다.
- `CategoryService`(생성/목록 조회)를 노출하는 컨트롤러가 없어, 카테고리를 등록·조회할 API 경로 자체가 없다. 도달 불가능한 코드다.

따라서 (1) 템플릿의 카테고리 무결성을 어떻게 강제할지, (2) 카테고리를 어떤 방식으로 관리 리소스화할지 정한다.

## 결정 (Decision)

1. **`Template.category`는 문자열 컬럼을 유지**하되, **템플릿 등록 시 해당 카테고리가 `category` 테이블에 존재하는지 앱(서버)에서 검증**한다. 존재하지 않으면 400으로 거절한다. DB FK로 강제하지 않는다.

2. **카테고리를 관리 리소스로 노출한다.** 카테고리 생성(`POST`)과 목록 조회(`GET`) 엔드포인트를 추가한다. 관리자가 카테고리를 먼저 등록한 뒤, 그 카테고리로만 템플릿을 등록할 수 있다.

3. **`CategoryServiceImpl`의 예외 처리를 공통 규약에 맞춘다.** 광범위한 `catch (Exception)`로 원인을 삼켜 500으로 뭉개지 않고, 중복 등 예측 가능한 실패는 적절한 `BusinessException`(409 등)으로 매핑한다.

이 결정은 ADR-002가 "데이터 무결성은 앱(서버 검증)이 책임진다"고 정한 방향과 일치한다.

## 고려한 대안 (Alternatives Considered)

### 대안 1: `Template.category`를 `Category`와 FK(@ManyToOne)로 연결
- 설명: 문자열 대신 `Category` 엔티티 참조로 바꿔 DB 레벨 참조 무결성을 강제.
- 장점: DB가 존재하지 않는 카테고리 저장을 원천 차단, 참조 중인 카테고리 삭제 방지.
- 단점: 스키마 마이그레이션 필요, 응답 DTO·조회 경로 변경, 카테고리 이름 변경 시 전파 고민 필요. ADR-002의 "category = 문자열 필드" 모델을 뒤집는다.
- 채택하지 않은 이유: 초기 단계에서 비용 대비 이득이 낮고, 앱 검증으로 동일한 사용자 경험(잘못된 카테고리 거절)을 얻을 수 있다. 무결성을 앱이 책임진다는 ADR-002 기조와도 맞다. 필요해지면 후속 ADR로 승격 가능.

### 대안 2: 카테고리를 enum(코드 고정)으로 관리
- 설명: 카테고리를 자바 enum으로 고정하고 검증.
- 장점: 타입 안전, 별도 테이블·검증 조회 불필요.
- 단점: 카테고리 추가마다 코드 수정·재배포 필요. "관리자가 DB로 관리"하는 방향(ADR-002)과 충돌.
- 채택하지 않은 이유: 운영 유연성이 떨어진다. 이미 `Category` 테이블이 존재한다.

## 결정 이유 (Rationale)

- **일관성**: ADR-002가 정한 "무결성은 앱이 책임, category는 문자열" 모델을 유지하면서 실제 검증만 채운다.
- **최소 변경**: 스키마 마이그레이션 없이 기존 엔티티/리포지토리를 그대로 활용한다.
- **운영 유연성**: 카테고리는 코드가 아닌 데이터로 관리되어 재배포 없이 추가·조회된다.

## 영향 (Consequences)

### 긍정적 영향
- 존재하지 않는 카테고리로의 템플릿 등록이 차단된다(400). `TemplateServiceImpl.createTemplate`가 `CategoryService.validateExists`로 검증한다.
- `TemplateCreateRequest.category`에 `@NotBlank`를 두어 빈 카테고리는 요청 검증 단계에서 400으로 걸러진다.
- 카테고리 등록·조회 API(`CategoryController`: `POST /api/category/v1`, `GET /api/category/v1`)가 생겨 카테고리가 실제 관리 가능한 리소스가 된다.
- 카테고리 중복 등록 실패가 `DUPLICATE_CATEGORY`(409), 미존재가 `CATEGORY_NOT_FOUND`(400)로 공통 에러 포맷으로 일관되게 응답된다. `CategoryServiceImpl`의 광범위한 `catch(Exception)`는 제거됐다.

### 부정적 영향 / 트레이드오프
- DB 레벨 FK가 없어, 카테고리 삭제 시 해당 문자열을 참조하던 템플릿이 논리적으로 고아가 될 수 있다(현재 카테고리 삭제 기능은 없음).
- 템플릿 등록마다 카테고리 존재 확인 조회(`existsByTitle`)가 1회 추가된다.

### 후속 조치 필요 사항
- ~~카테고리 검증 실패용 ErrorCode 추가(`CATEGORY_NOT_FOUND` 400).~~ 완료
- ~~카테고리 중복 등록용 ErrorCode 추가(`DUPLICATE_CATEGORY` 409).~~ 완료
- 카테고리 삭제 기능 도입 시 참조 중 템플릿 처리 정책 결정.
- 무결성 요구가 커지면 대안 1(FK)로의 승격 검토.
