# ADR-009: 청첩장 저장 모델 — sectionId 키잉, 단계별 검증, 서버 경유 사진 업로드

- 상태: 승인됨
- 작성일: 2026-07-21
- 작성자: jasmin
- 관련 ADR: ADR-001(부분 개정), ADR-002(승계), ADR-007(구체화), ADR-008(패턴 확장)

## 배경 (Context)

템플릿·컴포넌트·옵션 관리가 구현되어, 이제 사용자가 실제로 만든 **청첩장(Invitation)을 저장하는 경로**를 열어야 한다. 그런데 현재 `Invitation` 엔티티는 ADR-002 시절 모델에 멈춰 있어 이후 결정과 어긋나 있다.

- `section_values`(jsonb) 하나만 있고, ADR-007 결정 4가 함께 두기로 한 **`selected_options`가 없다.**
- `section_values`의 **키가 무엇인지 정의되어 있지 않다.** ERD 예시는 `"cover"`, `"gallery"` 같은 섹션 이름을 쓰지만, ADR-007은 템플릿을 "같은 컴포넌트를 여러 번 쓸 수 있는 순서 있는 레시피"로 재정의했다. 이름 키로는 `gallery ×2` 조합의 값을 구분할 수 없다.
- 실제로 `Template.sections`의 각 원소에는 **인스턴스 식별자가 없다.** `componentUId`와 고정옵션값만 있다.
- 외부 노출 식별자가 없어 편집 API가 PK(`invitation_id`)를 그대로 써야 한다. `Template`은 이미 `template_uid`로 이 문제를 해결했다.

ADR-007은 후속 조치로 "실제 저장 endpoint·payload 형태 확인 후 `section_values`/`selected_options` 형태 확정"을 남겨 두었다. 이 ADR이 그 확정이다.

동시에 두 가지가 함께 결정되어야 저장 경로가 완성된다.

1. **검증 시점** — 편집 중 임시저장은 필드가 비어 있는 게 정상인데, `data_schema`의 `required`를 매 저장마다 강제하면 임시저장이 불가능해진다.
2. **사진 업로드 경로** — 청첩장 사진은 컴포넌트마다 개수와 필드 모양이 다르고(메인이미지 1장, 갤러리 N장), 업로드 방식은 ADR-001이 presigned 직접 업로드로 정해 두었으나 그 이후 S3 연동 코드는 ADR-008의 서버 경유 방식으로만 구현되어 있다.

**참고:** 참석여부(RSVP)·방명록처럼 하객이 남기는 데이터는 쓰기 주체(하객, 무인증)와 수명주기가 청첩장 본문(제작자 소유)과 다르므로 이 ADR의 범위에서 제외하고 별도 테이블·별도 ADR로 다룬다.

## 결정 (Decision)

**1. 섹션 인스턴스에 `sectionId`를 부여하고, `section_values`를 `sectionId`로 키잉한다.**
`Template.sections`의 각 원소는 `sectionId`(템플릿 내 고유)를 **필수**로 가진다. 템플릿 등록 검증(`validateRecipe`)에 `sectionId` 존재·중복 검사를 추가한다. `Invitation.section_values`는 `{sectionId → {필드값}}` 구조가 되고, ERD의 섹션 이름 키 예시는 폐기한다.

**2. `Invitation`에 `invitation_uid`(UUID)와 `selected_options`(jsonb)를 추가한다.**
`invitation_uid`는 `Template.template_uid`와 동일한 패턴의 외부 노출 식별자로, 모든 편집 API가 PK 대신 이것을 쓴다. `selected_options`는 ADR-007 결정 4대로 사용자가 고른 옵션값을 담으며, 템플릿에서 `editable: true`로 열어 둔 옵션만 허용한다.

**3. 검증을 저장 단계에 따라 나눈다 — DRAFT는 구조만, PUBLISHED는 전부.**

| 검사 | DRAFT 저장 | 발행(publish) |
|---|---|---|
| `section_values`의 키가 템플릿의 `sectionId` 집합에 속하는가 | ✅ | ✅ |
| `selected_options`가 `editable` 옵션이고 허용값인가 | ✅ | ✅ |
| 이미지 키가 본인 소유의 업로드 기록인가 | ✅ | ✅ |
| `Component.data_schema` 전체 검증(`required` 포함) | ❌ 건너뜀 | ✅ |

즉 **구조·권한 검증은 항상**, **완결성 검증은 발행 시점에** 한다. 임시저장이 반쯤 채운 상태를 받아들이면서도, 하객에게 노출되는 것은 완전한 데이터만이 되도록 보장한다.

**4. 청첩장 사진도 서버 경유(multipart) 업로드를 쓴다. 이는 ADR-001의 부분 개정이다.**
전용 업로드 엔드포인트가 `MultipartFile`을 받아 S3에 올리고 객체 키(`invitations/{userId}/{uuid}.{ext}`)를 반환한다. DB에는 객체 키만 저장하고, 조회 응답을 만들 때마다 presigned GET URL로 치환한다(ADR-008과 동일). ADR-001의 "S3에 저장하고 데이터에는 키만 남긴다"는 유지되고, **업로드 경로만** presigned 직접 업로드 → 서버 경유로 바뀐다.

**5. 이미지 연결은 컴포넌트 구조를 모른 채 수행한다 — 프리픽스 재귀 스캔.**
저장 시 서버는 `section_values` 전체를 재귀 순회해 `invitations/` 프리픽스로 시작하는 문자열을 이미지 키로 수집한다. 수집한 키는 소유자 확인 후 `ImageUpload`를 `LINKED`로 전환하고, 직전 저장에 있었으나 이번에 사라진 키는 `ORPHANED`로 전환한다. 이미지 필드의 이름·개수·중첩 구조는 전적으로 `Component.data_schema`가 정의하며 서버는 알 필요가 없다. `ImageUpload`에는 업로더(`user_id`)를 추가해 남의 업로드 키를 붙일 수 없게 한다.

**6. 공개 조회는 렌더 페이로드를 합쳐서 내려준다.**
`GET /api/public/invitations/{slug}`는 `PUBLISHED` 상태에서만 응답하며, 템플릿의 `sections`·`theme`와 청첩장의 `section_values`·`selected_options`를 병합한 단일 페이로드를 반환한다. 하객 렌더러가 템플릿 API를 따로 호출하지 않아도 되게 한다.

## 고려한 대안 (Alternatives Considered)

### 대안 1: `section_values`를 `componentUId`로 키잉 — 채택하지 않음
- 설명: 템플릿 `sections`를 그대로 두고, 청첩장 값을 `{componentUId → 값}`으로 저장.
- 장점: 템플릿 스키마를 건드리지 않아 변경이 가장 작다.
- 단점: ADR-007이 명시적으로 허용한 "같은 컴포넌트 타입 반복(gallery ×2)"을 표현할 수 없다. 두 갤러리의 사진이 한 키에 뭉개진다.
- 채택하지 않은 이유: 조합 유연성이 ADR-007 재정의의 핵심 목적인데, 그것을 저장 계층에서 되돌리게 된다.

### 대안 2: `sections` 배열 인덱스를 키로 사용 — 채택하지 않음
- 설명: `section_values`를 `{0: …, 1: …}`처럼 템플릿 `sections` 순서와 1:1로 저장.
- 장점: 템플릿에 필드를 추가하지 않아도 된다.
- 단점: 템플릿의 섹션 순서를 바꾸거나 중간에 하나 끼워 넣는 순간 기존 청첩장의 값이 전부 어긋난다. 위치가 곧 의미인 구조는 데이터 이관 수단이 없다.
- 채택하지 않은 이유: 템플릿은 운영 중 수정되는 데이터인데, 그 수정이 이미 저장된 청첩장을 조용히 망가뜨린다.

### 대안 3: 매 저장마다 `data_schema` 전체 검증 — 채택하지 않음
- 설명: DRAFT/PUBLISHED 구분 없이 저장 시점마다 `required` 포함 전체 검증.
- 장점: 검증 규칙이 하나뿐이라 단순하고, DB에 항상 완전한 데이터만 들어간다.
- 단점: 편집 화면에서 한 필드만 채우고 나가는 임시저장이 불가능해진다. 클라이언트가 이를 우회하려면 완성 전 데이터를 로컬에 들고 있어야 하는데, 그러면 기기 변경 시 작업이 날아간다.
- 채택하지 않은 이유: 임시저장은 청첩장 제작(여러 세션에 걸친 긴 작업)의 필수 기능이다.

### 대안 4: `data_schema`에 이미지 필드를 표시하고 경로로 추출 — 채택하지 않음
- 설명: `data_schema`에 `x-image: true` 같은 커스텀 키워드를 두고, 서버가 그 경로의 값만 이미지 키로 읽는다.
- 장점: 추출 대상이 명시적이라 프리픽스 규칙에 의존하지 않는다.
- 단점: 중첩 객체·배열 안의 필드를 가리키려면 서버가 스키마 경로 해석기를 직접 만들어야 하고, 컴포넌트마다 구조가 달라 예외가 늘어난다. 표준 JSON Schema 밖의 커스텀 키워드라 검증 엔진도 무시한다.
- 채택하지 않은 이유: 얻는 정확도에 비해 구현·유지 비용이 크다. 프리픽스 재귀 스캔은 구조를 몰라도 동작하고, 잘못 수집하더라도 소유자 확인 단계에서 걸러진다.

### 대안 5: 청첩장 사진도 presigned 직접 업로드(ADR-001 원안 유지) — 채택하지 않음
- 설명: presigned PUT URL 발급 엔드포인트를 만들고 클라이언트가 S3에 직접 올린다.
- 장점: ADR-001과 일관되고, 갤러리 대량 업로드 시 사진 바이너리가 서버를 통과하지 않는다.
- 단점: presigned 발급 로직을 새로 구현해야 하고, 현재 구현된 S3 경로(`StorageService.upload`)를 재사용할 수 없다. 서버가 파일 내용을 보지 못해 타입·크기 검증이 약해진다.
- 채택하지 않은 이유: 아래 "결정 이유" 참고. 다만 이 대안은 **폐기가 아니라 유보**이며, 서버 부하가 실측으로 문제가 되면 되돌린다.

## 결정 이유 (Rationale)

- **ADR-007 재정의를 저장 계층까지 관통시킨다.** 조합 가능한 레시피라는 결정은 값을 인스턴스 단위로 식별할 수 있어야 성립한다. `sectionId`는 그 최소 비용이다.
- **템플릿 수정이 기존 청첩장을 깨지 않는다.** 인덱스가 아닌 안정적 식별자를 키로 쓰면, 섹션 순서 변경·추가가 이미 저장된 값과 독립적이다.
- **트러스트 경계는 유지하되 작업 흐름을 막지 않는다.** ADR-007 대안 3에서 거부했던 "검증 없는 blob 저장"으로 후퇴하지 않으면서, 완결성 검증만 발행 시점으로 미뤄 임시저장을 허용한다. 하객에게 깨진 청첩장이 노출되지 않는다는 제품 원칙은 그대로다.
- **사진 업로드는 구현 속도와 검증 강도를 우선한다.** ADR-001이 presigned를 고른 근거(대량·고화질 트래픽)는 여전히 유효하지만, 그것은 아직 실측되지 않은 부하 예측이다. 현재는 트래픽이 없고, 서버 경유는 이미 동작하는 `StorageService`를 그대로 쓰며 서버가 파일 내용을 직접 검증할 수 있다. 조기 최적화보다 동작하는 경로를 먼저 세우고, 부하가 실제로 관측되면 그때 presigned로 전환한다. **전환 비용은 업로드 엔드포인트 하나에 국한된다** — 저장 형태(객체 키)와 조회 방식(presigned GET)이 동일하기 때문이다.
- **서버가 컴포넌트 내부 구조를 몰라도 되게 한다.** 이미지 수집을 프리픽스 규칙으로 처리하면, 컴포넌트가 늘어나도 서버 코드는 그대로다. ADR-007이 노린 "컴포넌트 추가 = 데이터 추가"에 부합한다.

## 영향 (Consequences)

### 긍정적 영향
- 같은 컴포넌트를 여러 번 쓰는 템플릿에서도 값이 정확히 구분된다.
- 여러 세션에 걸친 청첩장 제작(임시저장)이 가능하다.
- 새 컴포넌트가 추가되어도 이미지 처리·검증 코드는 변경되지 않는다.
- 편집 API에 PK가 노출되지 않는다.
- 하객 렌더러가 API 한 번으로 필요한 데이터를 전부 받는다.

### 부정적 영향 / 트레이드오프
- **ADR-001의 업로드 경로 결정이 뒤집힌다.** 대량 업로드 시 서버 메모리·대역폭이 병목이 될 수 있고, 이는 실측으로 확인해야 한다.
- **`Template.sections`의 계약이 바뀐다.** `sectionId` 필수화로 기존에 등록된 템플릿이 있다면 백필이 필요하다(현재 운영 데이터 없음).
- **프리픽스 재귀 스캔은 정밀하지 않다.** 사용자가 `invitations/`로 시작하는 문자열을 텍스트 필드에 넣으면 이미지 키로 수집을 시도한다. 소유자 확인에서 걸러지므로 데이터가 오염되지는 않지만, 불필요한 조회가 발생한다.
- **DRAFT에는 불완전한 데이터가 들어간다.** DB 상태만 보고 "이 청첩장이 유효한가"를 판단할 수 없고, 항상 `status`를 함께 봐야 한다.
- **`selected_options`가 참조하는 `OptionDefinition`은 변할 수 있다.** 저장 시점에 허용됐던 값이 나중에 허용 목록에서 빠질 수 있다(ADR-007의 버전 관리 부재 리스크와 동일 성격).

### 후속 조치 필요 사항
- **본 ADR 승인 시 ADR-001에 "ADR-009로 부분 개정(청첩장 사진 업로드 경로)" 표기를 추가한다.**
- `docs/ERD.md`의 `invitations` 절과 `section_values` 예시를 새 구조로 갱신한다.
- RSVP·방명록 테이블 설계(별도 ADR).
- `ORPHANED` 이미지의 실제 S3 삭제 배치와 S3 lifecycle 규칙의 역할 분담(ADR-001 후속 과제와 통합).
- 업로드 파일 타입·크기 제한값 확정.
- 서버 경유 업로드의 부하 실측 후 presigned 전환 여부 판단.
- 발행 취소(unpublish) 시 slug 재사용 여부 정책.
