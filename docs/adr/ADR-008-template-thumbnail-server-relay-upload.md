# ADR-008: 템플릿 썸네일은 서버 경유(multipart) 업로드, 객체 키 저장 + 조회 시 presigned GET

- 상태: 승인됨
- 작성일: 2026-07-18
- 작성자: jasmin
- 관련 ADR: ADR-001 (사진 저장은 AWS S3, 업로드는 presigned URL 직접 업로드)

## 배경 (Context)

Template 생성 시 미리보기용 썸네일 이미지를 받아야 한다. 현재 `Template.thumbnail`(String)은
클라이언트가 넘긴 문자열을 그대로 저장만 하고, 프로젝트에는 S3 관련 코드(SDK 의존성, 클라이언트,
설정)가 아직 없다.

이미지 저장 방식은 이미 ADR-001에서 결정되어 있다. 다만 ADR-001은 **사용자(신랑·신부)가 올리는
청첩장 사진**을 대상으로 한다. 그 맥락은 다음과 같다.

- 청첩장 한 건에 다수의 고화질 이미지가 포함된다(대량·대용량).
- 업로드 주체는 일반 사용자이고, 트래픽이 크다.
- 그래서 서버 부하를 줄이기 위해 presigned URL 기반 클라이언트→S3 직접 업로드를 채택했다.

반면 **템플릿 썸네일**은 성격이 다르다.

- 템플릿당 1장, 관리자(템플릿 제작자)가 올린다.
- 저용량·저빈도라 서버 중계 비용이 문제되지 않는다.
- 템플릿 생성 요청과 함께 한 번에 처리되면 클라이언트/서버 약속이 단순해진다.

따라서 템플릿 썸네일에 한해 어떤 업로드 경로와 저장 형태를 쓸지 별도로 결정한다.

## 결정 (Decision)

**템플릿 썸네일은 서버 경유(multipart) 업로드를 사용한다.** 즉, 클라이언트가 `MultipartFile`을
서버로 보내면 서버가 검증 후 S3에 PutObject 한다. 이는 ADR-001의 사용자 사진 경로(presigned
직접 업로드)와 구분되는, 템플릿 썸네일 전용 정책이다.

**DB에는 S3 객체 키만 저장한다.** `templates.thumbnail` 컬럼에는 `templates/thumbnails/{uuid}.{ext}`
형태의 객체 키를 저장하고, 만료되는 URL은 저장하지 않는다.

**조회 응답을 만들 때마다 객체 키로부터 presigned GET URL을 생성해 내려준다.** presigned URL은
DB에도 Redis 캐시에도 저장하지 않으며, 캐시에는 객체 키가 담긴 응답을 저장하고 반환 직전에
URL을 새로 채운다.

## 고려한 대안 (Alternatives Considered)

### 대안 1: 템플릿 썸네일도 presigned 직접 업로드 (ADR-001과 동일)
- 설명: 서버가 presigned PUT URL과 객체 키를 발급하고, 클라이언트가 S3에 직접 올린 뒤 키를
  템플릿 생성 요청에 포함한다.
- 장점: ADR-001과 완전히 일관된다. 서버가 바이너리를 중계하지 않는다.
- 단점: 업로드 → 완료 통지 → 템플릿 저장의 다단계 흐름이 필요해, 저빈도·저용량인 썸네일에는
  과한 복잡도다. 고아 객체 관리 부담도 커진다.
- 채택하지 않은 이유: 썸네일은 관리자·저용량·저빈도라 서버 중계 비용이 문제되지 않고, 단일
  요청으로 끝나는 편이 클라이언트/서버 약속을 단순하게 만든다.

### 대안 2: presigned GET URL을 DB에 직접 저장
- 설명: 업로드 시점에 presigned GET URL을 만들어 `thumbnail`에 그대로 저장한다.
- 장점: 조회 로직이 가장 단순하다(값을 그대로 반환).
- 단점: presigned URL은 만료되므로, 만료 후에는 깨진 이미지가 된다. Redis 30일 캐시와 결합하면
  문제가 더 커진다.
- 채택하지 않은 이유: 운영상 이미지가 만료되어 깨지는 치명적 결함이 있다.

### 대안 3: 공개 URL(버킷/CloudFront) 영구 저장
- 설명: 버킷/객체를 공개 읽기로 두고 공개 URL을 저장, 조회 시 그대로 반환한다.
- 장점: 조회가 단순하고 CDN 캐싱에 유리하다.
- 단점: 버킷 공개 정책 또는 CloudFront 배포 설정이 선행되어야 한다.
- 채택하지 않은 이유: 현 시점에 CloudFront/공개 버킷 정책이 정해지지 않았다. presigned GET로
  먼저 서빙하고, CDN 연동은 후속으로 남긴다.

## 결정 이유 (Rationale)

- **맥락 적합성**: 템플릿 썸네일은 관리자·저용량·저빈도라, ADR-001이 우려한 "대량 사진 트래픽의
  서버 중계 비용" 문제에 해당하지 않는다. 서버 경유가 오히려 단순하고 충분하다.
- **운영 안정성**: 객체 키만 저장하고 조회 시 presigned GET를 생성하면, 만료 URL이 DB/캐시에
  고이지 않아 이미지가 깨지지 않는다. 버킷을 비공개로 유지할 수 있다.
- **기존 캐시와의 정합성**: 캐시에는 객체 키를 담고 반환 직전에 URL을 주입하므로, 30일 Redis
  캐시와 짧은 presigned 수명이 충돌하지 않는다.

## 영향 (Consequences)

### 긍정적 영향
- 단일 요청(multipart)으로 템플릿 생성과 썸네일 업로드가 끝나 흐름이 단순하다.
- S3 버킷을 비공개로 유지하면서 조회 시점마다 유효한 URL을 제공한다.
- ADR-001(사용자 사진)과 정책이 명확히 분리되어 각 맥락에 맞는 방식을 쓴다.

### 부정적 영향 / 트레이드오프
- **서버가 바이너리를 중계한다.** 썸네일은 저용량·저빈도라 부담이 작지만, 사용자 사진 경로와
  다른 방식이 공존하게 된다(의도된 분리).
- **고아 객체 가능성.** 썸네일을 S3에 올린 뒤 템플릿 저장이 실패하면 연결되지 않은 객체가 남을
  수 있다. 관리자·저빈도라 저위험으로 보고, 이번 범위에서는 ADR-001의 `ImageUpload` 고아 추적을
  연결하지 않는다. 필요 시 S3 lifecycle 규칙으로 정리한다.
- **조회마다 presigned 생성 비용.** 서명 연산이 요청마다 추가되나 경량이다.

### 후속 조치 필요 사항
- presigned 발급 제약(허용 content-type = `image/*`, 최대 크기) 값 확정.
- presigned GET TTL 값 확정.
- CloudFront 도메인 연동 여부는 별도 검토(현재는 presigned GET로 서빙).
- 업로드 API를 관리자 인증과 연계할지 확정(현재 인증 정책과 정렬).
