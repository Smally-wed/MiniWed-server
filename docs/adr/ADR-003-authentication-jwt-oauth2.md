# ADR-003: 인증은 JWT 기반, 로그인은 소셜+자체 병행, 공개 조회는 무작위 슬러그로 보호

- 상태: 승인됨
- 작성일: 2026-07-01
- 작성자: jasmin
- 관련 ADR: ADR-002

## 배경 (Context)

MiniWed는 별도 프론트엔드 + REST API 서버 구조이며([docs/ARCHITECTURE.md](../ARCHITECTURE.md)), 제작자(신랑·신부)는 로그인해 자신의 청첩장을 관리하고, 하객은 로그인 없이 고유 URL로 청첩장을 열람한다. 프로젝트에는 이미 Spring Security가 포함돼 있다.

다음을 결정해야 한다.
- 제작자의 인증(로그인 상태 유지) 방식
- 회원가입/로그인 수단
- 하객이 보는 공개 청첩장의 접근 경계
- 관리자/사용자 권한(역할) 구분 — 관리자는 템플릿을 관리한다

청첩장에는 계좌번호·전화번호 등 민감정보가 담기고 URL을 아는 사람은 열람할 수 있으므로, 공개 범위의 보호 수준도 함께 정한다.

## 결정 (Decision)

1. **인증은 JWT 토큰 기반으로 한다.** access token + refresh token 구조를 사용하고, 서버는 무상태로 동작한다. 클라이언트가 토큰을 보관하고 API 호출 시 제시한다.

2. **로그인 수단은 소셜 로그인(OAuth2)과 자체 이메일/비밀번호를 모두 지원한다.** 소셜(예: 카카오/구글)로 가입 장벽을 낮추고, 소셜을 쓰지 않는 사용자를 위해 자체 계정도 제공한다.

3. **하객 공개 페이지는 "조회 API만 비인증 공개 + 보호 장치" 방식(선택지 A)으로 한다.**
   - 청첩장 조회 GET API는 로그인 없이 접근 가능하다.
   - 생성·수정·삭제 등 나머지 API는 인증이 필요하다.
   - 슬러그는 **추측 불가능한 무작위 문자열**로 발급해 URL 유출 없이는 찾을 수 없게 한다.
   - **발행(published) 상태인 청첩장만** 공개하고, 작성 중(draft)은 비공개다.

4. **권한은 USER / ADMIN 역할로 구분한다.** 일반 사용자는 자신의 청첩장을 관리하고, 템플릿 관리 등은 ADMIN 권한으로 제한한다.

## 고려한 대안 (Alternatives Considered)

### 대안 1: 세션/쿠키 기반 인증
- 설명: 서버 세션 + 쿠키로 로그인 상태 유지.
- 장점: 구현이 직관적이고, 서버가 세션을 들고 있어 무효화(로그아웃)가 쉽다.
- 단점: 서버가 상태를 보관해야 해 수평 확장 시 세션 공유(스티키/외부 저장소)가 필요하다. 별도 프론트·모바일 환경에서 크로스도메인 쿠키 처리가 번거롭다.
- 채택하지 않은 이유: 별도 프론트 + REST API 구조에서는 무상태 JWT가 더 자연스럽고 확장에 유리하다.

### 대안 2: 소셜 로그인만 / 자체 계정만
- 설명: 로그인 수단을 하나로 단일화.
- 장점: 초기 구현량이 적다.
- 단점: 소셜만 두면 소셜 미사용자를 놓치고, 자체만 두면 가입 장벽이 높다.
- 채택하지 않은 이유: 대상 사용자층을 넓게 수용하기 위해 병행을 택했다. (초기 구현량 증가는 감수)

### 대안 3: 공개 조회도 링크 토큰 필요 (선택지 B)
- 설명: 하객도 링크에 포함된 별도 토큰이 있어야 청첩장을 열람.
- 장점: 보호 수준이 더 높다.
- 단점: 하객의 열람·공유 흐름이 번거로워진다.
- 채택하지 않은 이유: 청첩장은 링크 공유로 널리 열람되는 특성이 있어 과한 보호다. 무작위 슬러그 + 발행 상태 제한으로 충분하다고 판단했다.

## 결정 이유 (Rationale)

- **구조 적합성**: 별도 프론트 + REST API에는 무상태 JWT가 잘 맞고, 서버 수평 확장 시 세션 공유 부담이 없다.
- **사용자 저변**: 소셜+자체 병행으로 가입 편의와 포용성을 동시에 확보한다.
- **제품 특성에 맞는 보호**: 청첩장은 링크로 공유되는 반(半)공개 콘텐츠다. 무작위 슬러그 + 발행 상태 제한이 일반적인 보호 수준이며, 하객 UX를 해치지 않는다.
- **책임 분리**: USER/ADMIN 역할로 템플릿 관리 같은 운영 기능을 명확히 격리한다.

## 영향 (Consequences)

### 긍정적 영향
- 서버 무상태로 수평 확장이 쉽다.
- 소셜 로그인으로 가입 전환이 수월하다.
- 공개/비공개 경계와 역할 경계가 명확해 보안 설정이 단순해진다.

### 부정적 영향 / 트레이드오프
- **JWT 무효화가 어렵다.** 무상태 특성상 토큰 탈취·로그아웃 즉시 무효화가 까다롭다. → access 토큰 수명을 짧게, refresh 토큰 회전·저장 전략으로 보완이 필요하다.
- **계정 연결(account linking) 필요.** 같은 이메일로 소셜과 자체 가입이 겹칠 수 있어, 동일 사용자 식별·연결 정책이 필요하다.
- **공개 조회의 정보 노출.** URL(슬러그)을 아는 사람은 계좌번호 등 민감정보를 볼 수 있다. 이는 청첩장 특성상 감수하되, 무작위 슬러그로 완화하고 검색엔진 비노출(noindex) 처리가 필요하다.
- **OAuth2 연동 비용.** provider별 콜백/리다이렉트 URI, 클라이언트 시크릿 관리가 필요하다.

### 후속 조치 필요 사항
- JWT 서명 방식(HS256/RS256), access·refresh 토큰 수명, refresh 저장·회전 정책
- 토큰 무효화(로그아웃·강제 만료) 전략
- OAuth2 provider별 연동 및 자체 계정과의 account linking 정책
- 슬러그 생성 규칙(길이·문자셋·충돌 처리) 및 예측 불가능성 확보
- 청첩장 발행 상태 모델(`status`: draft/published 등)
- ADMIN 권한 부여 방식(초기 시드/수동 지정 등)
- Spring Security 설정: 공개 엔드포인트(조회 GET) 화이트리스트 및 나머지 인증 요구

## 2026-07-14 구현 시 확정 사항 (OAuth 소셜 로그인)

설계·계획: [docs/superpowers/specs/2026-07-14-oauth-login-design.md], [docs/superpowers/plans/2026-07-14-oauth-login.md].

- **OAuth 흐름 = 토큰 릴레이**: 프론트가 provider(카카오·구글·네이버) access token을 받아 `POST /api/auth/v1/oauth/{provider}`로 전달 → 서버가 provider userinfo API로 검증·정규화 후 자체 JWT 발급. (Spring `oauth2Login` 리다이렉트 방식 미사용.)
- **account linking 정책 확정**: 소셜 이메일이 기존 User 이메일과 같으면 **provider가 이메일을 검증(`email_verified`)한 경우에만** 자동 링킹. 미검증인데 기존 User가 있으면 거부(`OAUTH_EMAIL_NOT_VERIFIED`, 409) — 미검증 이메일로 인한 계정 탈취 방지. 이메일 미제공(동의 안 함)은 가입 거부(`OAUTH_EMAIL_REQUIRED`). (네이버는 검증 플래그를 제공하지 않아 provider 정책상 검증된 것으로 간주 — 공식 문서 재확인 권장.)
- **잔여 리스크(후속)**: token-audience 미검증(다른 앱용 토큰 수용 가능성, confused-deputy) — 최소 구글은 `aud`/`azp` 대조 권장. 동시 최초 로그인 시 unique 제약 레이스는 현재 미처리(raw 500 가능).
