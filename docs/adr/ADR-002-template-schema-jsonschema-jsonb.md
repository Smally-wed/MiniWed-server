# ADR-002: 템플릿 섹션 스키마는 JSON Schema, 청첩장 입력값은 jsonb로 저장·검증

- 상태: 제안됨
- 작성일: 2026-06-30
- 작성자: jasmin
- 관련 ADR: ADR-001

## 배경 (Context)

[docs/ARCHITECTURE.md](../ARCHITECTURE.md)에서 "데이터/렌더러 분리"와 "입력 검증은 서버 책임"을 정했다. 이제 그 *책임*을 **어떻게 구현**할지 정해야 한다.

- 템플릿마다 요구하는 섹션·필드가 다르다. (예: 인사말 섹션은 `greeting_text`, 갤러리 섹션은 `photos`)
- 사용자가 보낸 청첩장 데이터(JSON)가 선택한 템플릿의 요구를 지키는지 서버가 저장 전에 검증해야 한다. 깨진 청첩장이 하객에게 노출되면 안 된다.
- 템플릿 관리는 현재 이 서버에서 하며, 관리자가 템플릿을 등록한다. 가능하면 새 템플릿의 **검증 규칙 추가가 서버 코드 재배포 없이** 이루어지는 게 바람직하다.

따라서 (1) 섹션 스키마를 무엇으로 정의·검증할지, (2) 사용자 입력값을 DB에 어떤 형태로 저장할지를 결정한다.

## 결정 (Decision)

1. **섹션 스키마는 JSON Schema 표준으로 정의한다.** 템플릿 메타데이터에 해당 템플릿의 JSON Schema를 함께 저장하고, 청첩장 저장 시 JSON Schema 검증 라이브러리로 사용자 입력 JSON을 검증한다. 검증 로직을 직접 작성하지 않고 라이브러리에 위임한다.

2. **사용자 청첩장의 섹션 입력값은 PostgreSQL `jsonb` 단일 컬럼에 저장한다.** 섹션별 정규화 테이블로 쪼개지 않는다.

3. **검증 시점은 저장(write) 시점이다.** 템플릿의 JSON Schema로 검증을 통과한 입력만 저장한다. 실패 시 어느 필드가 틀렸는지를 담아 거절한다.

4. **템플릿 스키마 버전 관리는 현 단계에서 도입하지 않는다.** 필요해지면 후속 과제로 다룬다.

데이터 모델(잠정):
- `templates`: `template_id`, `name`, `thumbnail`, `category`, **`section_schema` (jsonb, JSON Schema 문서)**, variant 옵션 등
- `invitations`: `invitation_id`, `user_id`, `template_id`, `slug`, `status`, **`section_values` (jsonb)**

검증 흐름:
1. 청첩장 저장 요청 수신
2. `template_id`로 템플릿의 `section_schema` 로드
3. JSON Schema validator로 `section_values` 검증
4. 실패 → 400(틀린 필드 정보 포함) / 성공 → `section_values`를 jsonb로 저장

## 고려한 대안 (Alternatives Considered)

### 대안 1: 자체 필드 정의(커스텀) 방식
- 설명: 표준 JSON Schema 대신, 자체적으로 정한 단순 구조(필드명·타입·필수·길이 목록)로 스키마를 정의하고 검증 로직을 직접 구현.
- 장점: 딱 필요한 만큼만 단순, 학습 비용 낮음, 외부 의존성 없음.
- 단점: 표현력이 직접 구현한 만큼으로 제한됨. 중첩·조건부 검증 요구가 늘면 사실상 JSON Schema를 재발명하게 되고, 검증 로직 유지보수가 우리 몫이 된다.
- 채택하지 않은 이유: 초기엔 단순하지만 요구가 커질수록 비용이 커진다. 표준의 표현력·생태계를 포기할 이유가 약하다.

### 대안 2: 코드로 고정 타입(섹션별 DTO + Bean Validation)
- 설명: 섹션마다 자바 record/class를 정의하고 `@Valid`로 검증.
- 장점: 타입 안전, IDE 지원, 자바 생태계 표준.
- 단점: 새 섹션·필드 추가 시 자바 코드 수정과 서버 재배포가 필요하다. 스키마가 코드에 박혀 "관리자가 DB로 템플릿을 등록"하는 방향과 충돌한다.
- 채택하지 않은 이유: 템플릿 검증 규칙이 코드와 강결합되어 운영 유연성이 떨어진다.

### 대안 3: 입력값을 정규화 테이블로 저장
- 설명: 섹션·필드를 관계형 테이블로 분해해 저장.
- 장점: DB 레벨 무결성·타입 제약이 강하고, 특정 필드 기준 쿼리·집계가 쉽다.
- 단점: 템플릿마다 필드가 가변이라 정규화 시 EAV 안티패턴으로 흐르기 쉽고 복잡·비효율적이다. 새 섹션·필드마다 스키마 변경이 필요하다. 청첩장은 "한 건 통째로 읽기"가 대부분이라 정규화 이점이 작다.
- 채택하지 않은 이유: 가변 스키마 + 통째 읽기라는 제품 특성에 jsonb가 더 맞는다.

## 결정 이유 (Rationale)

- **운영 유연성**: JSON Schema는 스키마가 데이터(DB)이므로, 새 템플릿의 검증 규칙 추가에 서버 재배포가 필요 없다. "관리자가 서버에서 템플릿을 등록"한다는 방향과 일치한다.
- **표현력·생태계**: JSON Schema는 필수·타입·길이·패턴·중첩을 표준 문법으로 표현하고, 검증을 성숙한 라이브러리에 위임할 수 있다.
- **제품 특성 적합**: 템플릿마다 필드가 다르고(가변 스키마), 청첩장은 보통 통째로 읽으므로 jsonb 단일 컬럼이 마이그레이션 부담 없이 잘 맞는다.
- **책임 일관성**: 무결성을 앱(서버 검증)이 책임지기로 이미 정했으므로, DB 레벨 제약이 약한 jsonb의 단점이 상쇄된다.

## 영향 (Consequences)

### 긍정적 영향
- 새 템플릿의 검증 규칙 추가가 코드 배포 없이 데이터 작업으로 가능하다(서버 측 검증 한정).
- 템플릿마다 다른 필드를 마이그레이션 없이 수용한다.
- 프론트가 JSON으로 소비하므로 저장값을 그대로 내려주기 쉽다.

### 부정적 영향 / 트레이드오프
- **DB 레벨 무결성이 약하다.** 특정 필드의 NOT NULL/FK를 DB가 보장하지 못하므로, 앱(서버) 검증을 신뢰하는 것이 전제다.
- **JSON Schema 작성 위험.** 스키마를 잘못 쓰면 검증이 헐겁거나 과하게 막힌다. 따라서 **관리자가 등록하는 스키마 자체의 유효성(메타 검증)**이 필요하다.
- **검증 라이브러리 의존성**이 추가된다.
- **스키마 변경 시 기존 데이터 호환** 문제가 잠재한다. 버전 관리를 도입하지 않기로 했으므로, 운영 중 스키마를 바꾸면 기존 청첩장 데이터와 어긋날 수 있다. → 후속 과제.

### 후속 조치 필요 사항
- JSON Schema 검증 라이브러리 선정 및 draft 버전 결정 (예: networknt/json-schema-validator)
- jsonb 컬럼의 JPA/Hibernate 매핑 방식 결정
- 검증 실패 응답 포맷(틀린 필드·이유) 설계
- 관리자 등록 스키마의 메타 검증(등록되는 JSON Schema 자체가 유효한지) 방법
- 스키마 버전 관리 정책 (필요 시 별도 ADR)
