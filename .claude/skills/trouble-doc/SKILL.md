# 트러블슈팅 문서 작성

## 언제 작성하는가
다음과 같은 작업을 했을 때 적용한다.
- 빌드/배포 실패 원인 분석 및 해결
- 런타임 에러, 예외 발생 원인 분석
- 성능 저하, 타임아웃 등 비정상 동작 분석
- 원인이 불명확해 여러 번 시도 끝에 해결한 경우

다음은 작성하지 않는다.
- 처음부터 의도대로 동작한 정상 구현
- 단순 오타/문법 오류 (디버깅 과정이 없었던 경우)

## 파일명 규칙
`docs/TROUBLE-{영문-kebab-case-요약}.md`

- 영문 소문자, 단어는 하이픈으로 연결
- 핵심 증상이나 원인을 3~5단어로 요약
- 예: `docs/TROUBLE-image-upload-timeout.md`, `docs/TROUBLE-gradle-build-oom.md`

## 문서 구조

```markdown
# {제목}

- 발생일: {YYYY-MM-DD}
- 영향 범위: {예: 이미지 업로드 API 전체 / 로컬 빌드만}
- 심각도: 낮음 | 보통 | 높음 | 긴급

## 증상
무엇이 어떻게 잘못 동작했는지 관찰된 사실 그대로 적는다. 에러 메시지, 로그, 스택트레이스 일부를 포함한다.

## 원인 분석
시도한 순서대로 가설과 검증 과정을 적는다. 막다른 길로 판명된 시도도 남긴다 (다음에 같은 길을 반복하지 않도록).

## 해결 방법
최종적으로 적용한 수정 내용. 변경한 파일/설정을 명시한다.

## 재발 방지
같은 문제가 다시 생기지 않도록 추가한 장치가 있다면 적는다 (테스트 추가, 모니터링, 문서화 등). 없다면 "없음"이라고 명시한다.

## 참고
관련 이슈, PR, 외부 문서 링크
```

## 절차
1. 문제 해결이 끝나면 위 파일명 규칙에 맞춰 파일을 생성한다.
2. 디버깅 중 나눴던 가설과 시도를 최대한 그대로 기록한다 (사후에 깔끔하게 재구성하지 않는다 — 막다른 시도도 가치가 있다).
3. 작성 후 사용자에게 파일 경로를 알리고 내용 확인을 요청한다.
