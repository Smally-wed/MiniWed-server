# ADR 작성 워크플로우

## 언제 이 스킬을 쓰는가
다음 중 하나에 해당하면 적용한다.
- 새로운 기능/모듈 추가
- 기존 아키텍처 구조 변경
- DB 스키마 변경
- 외부 서비스 연동 추가/교체
- 인증/인가 방식 변경
- 주요 라이브러리, 프레임워크 버전 교체

다음은 적용하지 않는다.
- 오타, 포맷팅, 단순 버그 수정
- 기존 ADR 범위 안에서의 구현 디테일

## 절차

1. **관련 ADR 탐색**
   `docs/adr/` 하위 파일명을 훑어 현재 작업과 관련된 ADR이 있는지 확인한다.
   ```
   ls docs/adr/
   grep -ril "<관련 키워드>" docs/adr/
   ```

2. **ADR이 있는 경우**
   해당 ADR의 "결정", "영향", "트레이드오프" 섹션을 먼저 읽고, 그 결정을 위반하지 않는 방향으로 작업을 진행한다. 만약 작업이 기존 ADR과 충돌한다면 바로 코드를 고치지 말고 사용자에게 먼저 알린다.

3. **ADR이 없는 경우**
    - `templates/ADR.md`를 복사해 `docs/adr/ADR-{다음 번호 3자리}-{kebab-case-제목}.md`로 생성한다.
      예: `docs/adr/ADR-007-image-upload-async.md`
    - 번호는 `docs/adr/` 안의 기존 파일 중 가장 큰 번호 + 1로 정한다.
    - "배경", "결정", "고려한 대안", "결정 이유", "영향" 섹션을 실제 내용으로 채운다. 대안은 최소 1개 이상 비교한다.
    - 상태는 우선 `제안됨`으로 둔다.
    - 작성이 끝나면 코드 작업을 진행하기 전에 **반드시 사용자에게 ADR 초안을 보여주고 검토/승인을 요청한다.** 승인 전에는 구조 변경 코드를 작성하지 않는다.
    - 사용자가 승인하면 상태를 `승인됨`으로 바꾸고 작업을 진행한다.

4. **작업 완료 후**
   ADR의 "영향" 섹션에 실제로 발생한 변경 사항이 있다면 갱신할지 사용자에게 확인한다.

## 체크리스트
- [ ] 관련 ADR 존재 여부 확인했는가
- [ ] 없다면 템플릿 기반으로 작성했는가
- [ ] 대안을 최소 1개 이상 비교했는가
- [ ] 코드 작업 전에 사용자 검토를 받았는가
